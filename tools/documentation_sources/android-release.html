Android release signing: required before publishing

Run the commands in this guide from Main_File/flutter_app. Finish the existing branding, identifiers, icon and splash instructions and Firebase and API configuration first. The separate iOS instructions still apply to iPhone releases.

Required before any release build: the supplied Gradle configuration selects the Android debug signing configuration when android/key.properties is absent. This documentation update does not change that source file. Apply the fail-closed Gradle configuration in step 3 before building a release. A successful build with the original configuration does not prove production signing. Always verify the certificate of the exact output you intend to upload, using step 5 below.

Every buyer must use their own upload key. This package intentionally includes no private keystore or passwords. For an existing Play application, use its registered upload key; do not create a replacement key unless you follow Play Console's upload-key reset process.

1. Create your buyer upload keystore

Use the JDK selected by Flutter; flutter doctor -v reports its Java binary path. keytool and jarsigner are in the same JDK bin directory. If the commands are not found, add that directory to PATH in your terminal. In PowerShell you can instead invoke its full quoted executable path with & "C:/path/to/jdk/bin/keytool.exe", followed by the arguments below. Use the JDK compatible with the project's Android Gradle plugin.

From Main_File/flutter_app, run this single-line command in PowerShell, Command Prompt, macOS or Linux:

keytool -genkeypair -v -keystore android/app/upload-keystore.jks -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias upload
  1. Choose a strong keystore password when prompted and repeat it. Password entry is hidden.
  2. Enter your own name/organization, organizational unit, city, state and two-letter country code. Confirm the resulting certificate identity when prompted. Do not use the identity Android Debug.
  3. At the key-password prompt, press Enter to use the same password as the keystore, or enter a separate password and retain both.
  4. The file is now Main_File/flutter_app/android/app/upload-keystore.jks. This is next to android/app/build.gradle.kts. Do not rerun the command to overwrite an existing production key. Back up the keystore, alias and passwords securely.

The upload alias identifies the private-key entry. -storetype JKS makes the format explicit and permits a separate key password. The key and self-signed certificate are created locally; no seller key is used.

2. Explain and configure every key.properties field

Copy android/key.properties.example to android/key.properties. In PowerShell run:

Copy-Item android/key.properties.example android/key.properties

On macOS/Linux use cp android/key.properties.example android/key.properties, or copy it in your file manager. Replace all password placeholders in the new file:

storePassword=CHANGE_ME_KEYSTORE_PASSWORD
keyPassword=CHANGE_ME_KEY_PASSWORD
keyAlias=upload
storeFile=upload-keystore.jks
Field Required value
storePassword The keystore password entered at the first keytool prompt. This opens the keystore.
keyPassword The password for the private-key entry. Use the same value as storePassword if you pressed Enter at the key-password prompt.
keyAlias The exact alias used in keytool, upload in this example. For an existing keystore, use its actual private-key alias.
storeFile The keystore path resolved by file(...) in android/app/build.gradle.kts. Relative paths start at android/app, not at flutter_app or at the key.properties directory. Thus upload-keystore.jks resolves to android/app/upload-keystore.jks. The old example ../app/upload-keystore.jks resolves to that same file.

For a keystore kept outside the project, use an absolute path, for example storeFile=C:/Users/YourName/private-keys/upload-keystore.jks on Windows or storeFile=/Users/yourname/private-keys/upload-keystore.jks on macOS. Do not use ~ or environment-variable expressions; Java Properties does not expand them. Prefer forward slashes on Windows. A literal backslash must be doubled, for example C:\\Users\\YourName\\private-keys\\upload-keystore.jks.

This is a Java Properties file: do not wrap values in quotes or append inline comments. A literal backslash in a password must be written as \\; enter other password characters exactly. Keep key.properties, *.jks and *.keystore private and excluded from version control, source distributions and public web folders.

3. Remove the debug fallback before building a release

This is a required buyer source change. In android/app/build.gradle.kts, retain the existing imports, plugins, keystoreProperties loading, SDK settings, Flutter configuration and dependencies. Inside the existing android { ... } block, replace the entire existing signingConfigs and buildTypes blocks with the following. Do not append duplicate blocks:

    signingConfigs {
        create("release") {
            keyAlias = keystoreProperties.getProperty("keyAlias")
            keyPassword = keystoreProperties.getProperty("keyPassword")
            storeFile = keystoreProperties.getProperty("storeFile")
                ?.takeIf { it.isNotBlank() }?.let { file(it) }
            storePassword = keystoreProperties.getProperty("storePassword")
        }
    }

    buildTypes {
        release {
            // Never select signingConfigs.getByName("debug") here.
            signingConfig = signingConfigs.getByName("release")
        }
    }

Then add this validation task at the top level of the same file, outside and after the closing brace of android { ... }:

val validateBuyerReleaseSigning = tasks.register("validateBuyerReleaseSigning") {
    doLast {
        fun signingError(reason: String): Nothing = throw GradleException(
            "Release signing blocked: $reason Configure android/key.properties " +
                "with your buyer upload keystore. Debug signing is forbidden for release."
        )
        if (!keystorePropertiesFile.isFile) {
            signingError("android/key.properties is missing.")
        }
        val invalid = listOf("storeFile", "storePassword", "keyAlias", "keyPassword").filter {
            val value = keystoreProperties.getProperty(it)
            value.isNullOrBlank() || value.startsWith("CHANGE_ME")
        }
        if (invalid.isNotEmpty()) {
            signingError("Missing or placeholder fields: ${invalid.joinToString()}.")
        }
        val store = file(keystoreProperties.getProperty("storeFile"))
        if (!store.isFile) signingError("The configured storeFile does not exist.")
        if (keystoreProperties.getProperty("keyAlias").equals("androiddebugkey", true) ||
            store.name.equals("debug.keystore", true)) {
            signingError("Use your buyer upload key, not the Android debug key.")
        }
    }
}

tasks.configureEach {
    if (name == "preReleaseBuild" || name == "validateSigningRelease") {
        dependsOn(validateBuyerReleaseSigning)
    }
}

For the supplied project without flavors, this check runs in the release APK and AAB pipelines and fails for missing/placeholder properties, a missing keystore or conventional Android debug key names. Android's signing task checks the keystore password, key password and alias. Debug development builds continue using their normal debug signing and do not need the buyer upload keystore. The name checks do not identify a renamed debug key: certificate verification in step 5 remains mandatory.

To test the guard after applying it, run ./gradlew :app:validateBuyerReleaseSigning from android (.\gradlew.bat :app:validateBuyerReleaseSigning in PowerShell). With valid buyer properties it must succeed. Temporarily rename key.properties to key.properties.saved, run the same task and require Release signing blocked: android/key.properties is missing.. Restore the filename immediately afterward. With the file absent, a release build must fail; do not restore the original debug fallback to bypass the error.

4. Build the signed Android App Bundle

Supply your Firebase Android client file and configure the matching application ID and API values first. Set your real Socket.IO/share configuration as explained in Flutter configuration; the following command shows the API overrides. Run from flutter_app:

flutter clean
flutter pub get
flutter build appbundle --release --dart-define=TOMCHAT_API_BASE_URL=https://api.example.com/ --dart-define=TOMCHAT_API_KEY=YOUR_API_KEY

For this project's non-flavored Gradle configuration, the signed bundle is Main_File/flutter_app/build/app/outputs/bundle/release/app-release.aab, or build/app/outputs/bundle/release/app-release.aab relative to flutter_app. Check the actual output path printed by Flutter after a successful build; some Flutter versions name the file app.aab. Use that exact fresh file in all verification commands if its name differs. A failed build may leave an older artifact; never upload that stale file.

5. Verify the AAB signature and buyer upload certificate

From flutter_app, run all three commands. The first checks the signed bundle's integrity; the next two let you compare the signer's certificate to your upload key:

jarsigner -verify -verbose -certs build/app/outputs/bundle/release/app-release.aab
keytool -printcert -jarfile build/app/outputs/bundle/release/app-release.aab
keytool -list -v -keystore android/app/upload-keystore.jks -alias upload
  1. Require jar verified. from jarsigner and inspect its warnings. Stop on an unsigned archive, invalid signatures, unsigned payload entries or disabled algorithms. A zero exit code alone does not prove that the archive is signed.
  2. A locally created upload certificate is self-signed. Warnings about a self-signed/untrusted certificate chain or absent timestamp can occur for an Android upload key; they do not establish that the wrong key was used. Investigate expired/not-yet-valid certificates and any other warnings before publishing. -strict can return a nonzero code for self-signed certificates, so do not interpret that status alone as proof of corruption.
  3. Compare the SHA-256 certificate fingerprint in the -printcert -jarfile output with the SHA-256 in -list -v for your upload alias. They must match exactly. If a different keystore location or alias was configured, use it in the third command. For multiple signers, inspect every signer and stop if any is unexpected.
  4. The matching certificate must be your buyer upload certificate. Stop if the subject is CN=Android Debug, the configured alias is androiddebugkey, or the fingerprints differ. You can also inspect your local debug certificate using the optional command below.
  5. For an existing Play app, compare against the Upload key certificate shown in Play Console's app-signing/app-integrity settings. On first enrollment, register/use this buyer upload certificate according to the console's signing setup.

Optional local debug-certificate comparison, if the default debug keystore exists (PowerShell):

keytool -list -v -keystore "$env:USERPROFILE/.android/debug.keystore" -alias androiddebugkey -storepass android

On macOS/Linux replace the keystore argument with "$HOME/.android/debug.keystore". The bundle's SHA-256 must not equal the debug certificate's SHA-256. These are certificate fingerprints, not a checksum of the AAB file.

Google Play App Signing: the upload key signs the submitted AAB; Google Play signs distributed APKs with the app signing key. Compare the local AAB to the upload certificate, not the Play app signing certificate. Register the appropriate SHA-1/SHA-256 fingerprints in Firebase/Google sign-in: debug for development, your release/upload key for locally installed releases, and the Play app signing certificate for Play-delivered builds. Recheck sign-in after installing through Play.

Optional: build and verify a release APK

flutter build apk --release --dart-define=TOMCHAT_API_BASE_URL=https://api.example.com/ --dart-define=TOMCHAT_API_KEY=YOUR_API_KEY
apksigner verify --verbose --print-certs build/app/outputs/flutter-apk/app-release.apk

apksigner is in your Android SDK build-tools/<installed-version> directory (apksigner.bat on Windows). Add that directory to PATH or invoke its full path. Require successful verification and compare the printed signer SHA-256 certificate digest to the buyer upload key above. Use jarsigner/keytool for an AAB; apksigner is for an APK.
